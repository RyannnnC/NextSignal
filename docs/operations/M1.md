# M1 operation and verification

## Local run

Requires Node.js 24, npm and Docker Desktop with a healthy Linux engine. Run from the repository root:

```sh
npm ci
npm run dev
```

Open http://127.0.0.1:3000 for the marketing homepage, then Start Free / Validate My Idea to enter /validate. Choose Alice or Bob as a local fixture account. Read the processing notice, submit a test idea, correct/confirm the profile, and start a fixture snapshot. Open View report from its summary to visit the private /projects/[projectId]/reports/[reportId] page; Back to project restores the selected project. Scenarios exercise missing data, contradictions, timeouts, malformed payloads and quotas. There is no external inference or market research. Every report is synthetic, not human reviewed and partial. /grow explains future capabilities only; pricing and research homepage sections clearly mark planned services/content.

The Next web process binds 127.0.0.1:3000. The local worker host binds 127.0.0.1:4311 and connects to Docker PostgreSQL on 127.0.0.1:54328. An ignored .local/runtime.json contains a rotating BFF capability. Sessions expire after one hour; sign out revokes the current session. Do not use these test accounts as production authentication. Do not share development ports. See [local development and database inspection](LOCAL_DEVELOPMENT.md).

Stop with Ctrl+C. Do not run two development hosts on the same ports. PostgreSQL retains its named volume; npm run db:stop stops it without deleting data. Environment secrets and .local must never be committed. On Windows, ignored files inherit filesystem ACLs; POSIX file mode alone does not establish Windows access control.

Local PostgreSQL storage, retained PGlite files and migration backups are not encrypted by the application; operating-system disk encryption and ACLs have not been verified. Use synthetic test ideas only. Production transport and storage encryption remain required.

## Initial schema and migration policy

The initial schema implements only M1 core tables. Claim types live in typed finding payloads and profile provenance; numeric metrics live in evidence payloads. Separate commercial tables, source snapshots, exports, competitor/keyword/experiment-outcome tables and production budget ledgers are deferred to their vertical slices, not represented by unused empty tables.

Apply migrations in filename order only to a reviewed local Supabase/PostgreSQL database with auth.users/auth.uid available. Local PGlite supplies its own development shim. Migration 0001 creates the M1 core; 0002 reaps expired leases after the final attempt. The local runner applies each migration and its checksum record atomically, and detects changed migration history. New schema changes require a new migration and forward/rollback documentation. Roll back in reverse order. The initial rollback is destructive and for local reset only; never apply it to production by assumption.

## Deletion and retention

Project deletion removes input text, profiles, consent, runs, jobs, evidence, finding links, actions and reports transactionally. A deletion status and content-free audit subject IDs remain. No report storage objects, analytics replicas or provider copies exist in M1. Local migration backups and the old PGlite source are retained separately and can contain previously deleted records; application deletion does not erase these snapshots. Logical deletion does not promise forensic disk erasure. Retention periods, backup-expiry handling and vendor deletion must be approved and tested before public data collection.
